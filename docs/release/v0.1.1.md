# StateNest v0.1.1

The first patch release after actually living with v0.1.0 — using it across real
projects, and getting it ready for a second computer. Everything here came from
something being wrong, unclear, or untested in practice.

## One view across personal and work

```bash
statenest dashboard --all-profiles --open
```

If you keep work and personal in separate profiles — and you should — you no
longer have to choose between that separation and seeing everything at once.

- **Read-only.** The dashboard refuses every HTTP verb except `GET`, so a
  unified view cannot write to the wrong profile. It cannot write at all.
- **Profiles stay separate.** Separate directories, separate sync repositories,
  nothing copied between them. This is a display-time join, not a merge.
- **Every project is labelled** with the profile it belongs to.
- **Servers stay where they were registered.** A work VPS never appears attached
  to a personal project.
- **Same-named projects are not merged**, in either direction.

The CLI deliberately did *not* grow `--all-profiles`. `projects`, `recent` and
`status` sit next to `checkpoint`, `task add` and `remove`, and a cross-profile
habit on the read commands is one that eventually gets typed next to a write.

## Safer multi-machine use

The same git repository on two computers is still **one** StateNest project with
**two** local locations — identity comes from the normalised git remote, so a
different path on a different machine changes nothing.

That was the intent before; it is now exercised end to end. Integration tests
drive a real bare repository through the whole sequence: first machine
initialises and syncs, second machine installs fresh with its own machine id,
syncs, sees the first machine's projects, checkpoints, tasks, decisions and
servers, then clones one repository at a different path and syncs back.

The awkward cases are covered too — a populated remote meeting an empty local, a
remote and a local that *both* already hold different data, two machines editing
different records, two machines editing the same record, going offline, a
credential being found, and an interrupted rebase. A same-record conflict stops
and shows you both versions; nothing is ever resolved in one side's favour
silently.

See [multi-machine.md](../multi-machine.md) for the step-by-step procedure.

## Better first-run and discovery

- **Accurate location wording.** `scan` used to announce that projects were
  "already known from another machine" when they were simply a second copy of
  the same repository on the computer in front of you. It now says which it is,
  because the claim comes from whether a location on another machine actually
  exists.
- **Same-name repositories are distinguishable.** Two unrelated repositories
  both called `threads` now list as `threads (work-org/threads)` and
  `threads (personal-org/threads)`. They were never merged — they were just
  impossible to tell apart. Ambiguous lookups now suggest qualifiers that
  actually resolve, instead of "use a longer or more specific name", which
  cannot work when the names are identical.
- **A real user guide.** [user-guide.md](../user-guide.md) explains the mental
  model, and [command-reference.md](../command-reference.md) documents every
  command and option — written from the CLI itself, with a test that checks the
  documentation never names a command that does not exist.

## Claude Code clarity

The integration did not change. What changed is that it is now explained
properly, because the most common misunderstanding was about what StateNest
knows:

- **`scan` does not read your Claude Code history.** It finds git repositories
  on disk. It never reads conversations.
- **SessionStart** injects a compact brief for a registered project — roughly
  600 characters of where you left off.
- **PostCompact** reuses the summary Claude Code has already generated to write
  a semantic checkpoint. StateNest never spawns a model of its own.
- **`/statenest:checkpoint` still matters.** A short, important session that
  never compacted may leave only metadata at SessionEnd — branch, commit, that
  work happened — and not what the work *meant*.
- StateNest cannot recover anything from before the integration was installed.

## Upgrade

```bash
npm install -g statenest@latest
statenest --version
```

Expected:

```
0.1.1
```

**Your existing `~/.statenest` data is preserved.** The on-disk schema is
unchanged from 0.1.0 — byte for byte — so there is no migration to run and
nothing destructive happens on upgrade.

## Security and privacy

Unchanged, and worth repeating:

- **Local-first.** Nothing leaves your machine unless you explicitly configure
  sync.
- **No raw Claude transcripts** are ever stored.
- **No source code** is stored. A handful of manifest files and a README are
  read for a description; nothing else.
- **The unified dashboard is read-only** and binds to loopback by default.
- **Profiles remain isolated** on disk and in sync.
- **Your sync repository must be private.** It holds project names, notes,
  server addresses and deploy paths. Sync scans for credentials before every
  push and refuses if it finds any.

Secret detection is a safety net with documented limits, not a guarantee — see
[security-model.md](../security-model.md).

## Provenance

This is the first StateNest release published by GitHub Actions through npm
Trusted Publishing, so it carries a provenance attestation linking the package
to the commit and workflow that built it. v0.1.0 was published by hand, because
npm cannot configure a trusted publisher for a package that does not exist yet,
and has no attestation.

Verify it yourself:

```bash
npm install statenest@0.1.1
npm audit signatures
```
