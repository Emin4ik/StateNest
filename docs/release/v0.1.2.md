# StateNest v0.1.2

An important multi-machine sync correctness patch. If you use the same StateNest
profile on more than one computer, update all of them.

## What was wrong

On v0.1.1, a successful sync could update machine-specific metadata inside a
**shared** profile file *after* the git sync had already finished. Two things
followed from that.

**Every successful sync left the profile dirty.** `statenest sync` would report
success, and `statenest sync status` immediately afterwards would report local
uncommitted changes with nothing ahead and nothing behind. Nothing was broken
yet, but the report was contradictory and there was no way to reach a clean
state.

**Two computers could manufacture a conflict out of nothing.** The field being
written was `last_sync_at` — when *this* machine last synced. Each computer
wrote a different value into the same shared line, so the second one to sync
hit:

```
Two machines changed the same record.
profile.yaml
```

even when the actual project data did not disagree at all. And because
`profile.yaml` is a control file rather than ordinary data, the conflict markers
made the whole profile unreadable, producing an error that contradicts itself:

```
No profile named "personal". Available profiles: personal
```

Nothing was ever lost — the data was intact the whole time — but the error
pointed in exactly the wrong direction, and the natural reaction to it (delete
`~/.statenest` and start over) is the one action that *would* lose data.

## What is fixed

- **The sync timestamp is machine-local.** `last_sync_at` now records when this
  computer synced, stored on this computer, where it cannot collide with
  anyone else's.
- **Scan roots are machine-local.** The directories StateNest scans are
  machine-specific — `~/Documents` on a Mac, `D:\work` on Windows. They used to
  be shared, so whichever machine synced last silently overwrote the others.
- **Shared profile metadata stays shared.** The profile name, description,
  `created_at` and sync remote are the same on every machine, and a genuine
  disagreement about them is still worth stopping on.
- **Joining a second machine no longer rewrites `created_at`.** A machine
  joining an established profile now takes the remote's value and leaves it
  alone.
- **A successful sync ends clean.** `git status` in the profile repository is
  empty after every successful sync. This is now a tested invariant, not an
  aspiration.
- **Ordinary conflicts are still surfaced.** Two machines genuinely editing the
  same record still stop and show you both versions. Nothing is auto-merged,
  and no automatic conflict resolution was added.
- **A conflicted profile now says what it is.** Instead of claiming the profile
  does not exist, the error names the file, recognises conflict markers, and
  tells you how to finish or abandon the rebase — and that your data is still
  there.

This is a repair of the existing sync design, not a new one. Sync still rebases
onto the remote, still keeps linear history, still scans for credentials before
every push, and still refuses to auto-merge.

## Upgrade

```bash
npm install -g statenest@latest
statenest --version
```

Expected:

```
0.1.2
```

**Update every machine that shares a profile, before resuming regular sync.**
This matters more than usual for this release. A machine still running 0.1.1
keeps writing `last_sync_at` into the shared profile, so it can still
manufacture the conflict — for itself and for every other machine on that
profile. The clean-after-sync guarantee only holds on machines running 0.1.2;
upgrading one of three does not give you a third of it.

Your existing `~/.statenest` data is preserved. The profile format is unchanged,
and the machine-local file seeds itself from what your profile already contains
the first time it is read, so your scan roots survive the upgrade. There is no
migration to run.

## If you are currently stuck on a `profile.yaml` conflict

Upgrading does not resolve a conflict that already exists — finish that first,
in the profile repository (`~/.statenest/profiles/<name>`):

```bash
git status                     # see which files are conflicted
# resolve profile.yaml by hand, keeping the shared values
git add profile.yaml
git rebase --continue
```

or `git rebase --abort` to back out and try again. Do not delete `~/.statenest`
and do not create a replacement profile; your checkpoints, tasks and decisions
are untouched by a conflict in this file.

## Security and privacy

Unchanged. Machine-local state holds a timestamp and a list of directory paths,
it stays on the machine that wrote it, and it is not a new category of data.
Credential scanning still runs before every push and still refuses to push if it
finds anything.
