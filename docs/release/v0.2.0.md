# StateNest v0.2.0

## Install once. Work normally.

```bash
npm install -g statenest
statenest setup

cd my-project
claude
```

That is the whole workflow now. An ordinary day of development needs no
StateNest commands at all.

Up to v0.1.2, StateNest was something you operated: register each repository,
remember to sync, resolve conflicts with raw git. It worked, but it asked you to
think about it. This release removes that.

## What happens by itself

- **Git repositories register themselves.** Open Claude Code in a repository
  with a remote and StateNest recognises it — same name, type and description
  logic as `statenest add`. No `add`, no `scan`. A clone of a project you
  already have is linked as another _location_ of the same project, not a
  second one.
- **Your context comes back.** Session start puts what you were doing in front
  of Claude: last session, open blockers, next actions.
- **What happened is remembered.** When Claude Code compacts, the summary it has
  already written becomes a checkpoint. At session end, one is written if the
  session did something. StateNest never runs a model of its own.
- **It syncs.** A checkpoint, decision or next action schedules a sync in the
  background, with a short pause so a burst of writes costs one push rather than
  five. You never type a git command.
- **Offline is normal.** Nothing waits for the network. Claude Code never starts
  slowly because your remote is slow, and never fails to start because you are
  offline. Local work continues exactly as usual and goes out when the network
  returns.

## Conflicts stop being frightening

If two machines change the same record, StateNest stops — it still never picks a
winner for you. What changed is what happens next.

Previously the attempted merge was left half-finished in your live profile.
When the conflicted file was `profile.yaml`, that made the profile unparseable
and took most commands down with it, producing the memorably unhelpful
`No profile named "personal". Available profiles: personal`.

Now the attempt is unwound. **Your local StateNest keeps working normally** while
the disagreement is outstanding. Both versions are kept, and:

```bash
statenest sync repair
```

shows you each one — named as work, not as a file path — and asks which to keep:

```
Sync conflict

  harbour — current state

    This machine:
      next: improve late-game AI

    The other machine:
      next: fix pathfinding

  Which version of "harbour — current state" should StateNest keep?

    1. Keep this machine
    2. Keep the other machine
```

No raw git. Normal output no longer mentions rebase, `HEAD` or
`origin/main...HEAD` at all — `statenest sync status --verbose` still shows the
underlying git state when you actually want it.

## A second computer

```bash
npm install -g statenest
statenest setup        # same private repository
```

It joins the existing profile, receives everything already there, and is ready.
You do not need to know that syncing comes before scanning, or what adopting a
remote history means. Your scan roots and sync settings stay local to each
machine; your projects, checkpoints, tasks and decisions are shared.

## Limitations, stated plainly

- **A short session that never compacted gets metadata, not meaning.** Branch,
  commit, that work happened — but not what it _meant_. Claude Code's supported
  hook data does not include per-turn content, and producing a rich summary
  without it would mean reading your raw transcript or running a second model.
  StateNest does neither. Run `/statenest:checkpoint` before you finish a short
  session that mattered.
- **A repository with no git remote is not registered automatically.** A
  project's identity is a hash of its remote; without one it gets a random id
  that cannot merge with the same directory on another machine, so registering
  them automatically would fill a shared profile with per-machine duplicates.
  `statenest add .` still registers it, because then you have said so.
- **There is no daemon.** Automatic sync runs when StateNest or Claude Code is
  active. A machine you never open never syncs.
- **Nothing is scanned automatically.** StateNest looks at the repository Claude
  Code was opened in — not its parent, not its siblings, not your home
  directory. `statenest scan` is still how you register things in bulk.
- **`sync repair` offers keep-mine or keep-theirs.** There is no "merge both",
  because no current record type can be safely combined without inventing a
  resolution you did not ask for.

## Upgrading from 0.1.2

```bash
npm install -g statenest@latest
statenest integrate claude
statenest doctor
```

**Run `statenest integrate claude` after upgrading.** Claude Code installs a
_copy_ of the plugin, so upgrading the npm package alone leaves it running the
previous one. That copy is self-consistent and keeps working — nothing breaks —
but you would not get any of this release. `integrate claude` now notices the
difference and updates it, and `doctor` tells you which version Claude Code is
actually running.

Your existing `~/.statenest` is preserved. The on-disk profile format is
unchanged, `statenest setup` is safe to re-run on an existing installation, and
machine-local settings migrate themselves on first read.

One configuration change: `sync.auto_pull` is retired. It lived in the shared
profile and was read by nothing. StateNest never force-pushes, so sending
requires rebasing onto the remote first — "pull" was never separable from "sync
at all", which is what the new machine-local `auto_sync` says. An existing
`auto_pull: false` is honoured once, as `auto_sync: false`.

The MCP tools are now named `statenest_*` rather than `projectbrain_*`, left
over from the pre-release name. The skills that call them shipped in the same
update, so the two cannot disagree.

## Security and privacy

Unchanged, and worth repeating now that more happens without you watching:

- **No source code is stored.** A handful of manifest files and a README are read
  for a description; nothing else. Automatic registration reads no more than
  `statenest add` always did.
- **No raw Claude Code transcripts are stored.** Ever.
- **Your source repositories are never written to.** StateNest reads git state
  and writes only inside `~/.statenest`.
- **Credentials still block a push.** The scan runs before anything leaves the
  machine. A finding pauses sync and records where to look — never what it saw.
- **There is no StateNest service and no account.** The sync remote is an
  ordinary private git repository you create and own.
